# Technical Limitations & Boundary Disclosures

MICROCODE INSPECTOR provides transparent embedded firmware extraction and analysis. To ensure technical integrity and prevent false expectations, this document details the boundaries, physical constraints, and irreversible transformations inherent to embedded binary analysis.

---

## 1. Fundamental Binary Analysis Realities

### The Compilation Gap (Loss of Metadata)
A compiled firmware binary is **not** the original source code (`.ino`, `.c`, or `.cpp`). During compilation and linking:
1. **Source Comments and Documentation**: Stripped entirely by the preprocessor before compilation begins.
2. **Preprocessor Directives & Macros**: Evaluated, expanded, or omitted; `#define`, `#ifdef`, `#include`, and compiler optimization flags leave zero traces in raw Flash.
3. **Variable and Function Identifiers**: Stripped by the linker unless debug symbols (DWARF/ELF) were explicitly retained (which raw Flash images do not contain). Local variables become register allocations or stack offsets (`SP + 4`); global variables become raw memory addresses.
4. **Data Structures and Types**: C/C++ `struct`, `class`, and `enum` definitions are flattened into primitive byte alignments and memory offsets.
5. **Control Flow Transformations**: Modern compilers (GCC `-O2`, `-Os`) unroll loops, inline functions, reorder instructions, vectorize operations, and eliminate dead code.

### Disassembly vs. Pseudocode Reconstruction
- **Disassembly** (`Assembly`): Mathematically verifiable recovery of raw machine opcodes into architecture-specific mnemonics. When the processor architecture, instruction set, and base load addresses are known, disassembly represents the **ground truth** of what is executed.
- **Decompilation / Approximate Logic** (`Pseudocode`): A synthetic approximation generated by analyzing control flow graphs, register usage, and standard idioms. It is an **interpretive hypothesis**, never the original source code. All pseudocode generated by MICROCODE INSPECTOR is explicitly tagged with confidence ratings and labeled as synthetic.

## 2. ESP32 Target Limitations

### Flash Encryption Architecture
- **Hardware AES Engine**: ESP32 integrates a hardware Flash encryption peripheral (AES-XTS-256 on classic ESP32, AES-128-XTS on newer variants) using an internal key burned into write-protected eFuses (`BLOCK1` / `BLOCK_KEY0`).
- **UART Readback Behavior**: When Flash Encryption is active (`FLASH_CRYPT_CNT` enabled), memory accessed by the CPU cache is transparently decrypted on the fly, but reading Flash directly via the UART ROM bootloader returns **ciphertext**.
- **Cryptographic Boundary**: MICROCODE INSPECTOR does **not** attempt to crack or bypass Flash Encryption. If ciphertext or encrypted partition tables are detected, the tool tags the dump as `ENCRYPTED/CIPHERTEXT` and halts analysis of code sections.

### Secure Boot vs. Flash Encryption
- **Secure Boot**: A cryptographic verification mechanism where the ROM bootloader verifies an RSA-3072 or ECDSA signature of the bootloader and application partition before allowing execution. **Secure Boot alone does not encrypt Flash contents.**
- **Secure Download Mode**: When `DIS_DOWNLOAD_MODE` or `UART_DOWNLOAD_DIS` eFuses are blown, the ROM bootloader permanently restricts or disables serial download operations. If a device has download mode disabled, UART readout is physically blocked.

### Partition Table Layout Variations
- ESP-IDF applications use configurable partition tables. While default tables reside at offset `0x8000` (or `0x9000` in certain configurations), custom bootloader builds may relocate the table or use custom encryption keys. If the partition table signature `0xAA50` is absent at probed locations, automated partition identification cannot proceed.

## 3. Arduino Uno / ATmega328P Target Limitations

### Optiboot Bootloader & STK_READ_PAGE Behavior
- The standard Arduino Uno R3 uses the **Optiboot** bootloader communicating via the STK500v1 protocol over USB-UART (ATmega16U2 or CH340).
- **STK_READ_PAGE Opcode (`0x74`, 't')**: While the STK500v1 specification defines `STK_READ_PAGE` for reading Flash and EEPROM pages, support depends on:
  1. **Bootloader Build Configuration**: Standard Optiboot builds include readback, but size-optimized builds (under 512 bytes) or third-party clones may omit `STK_READ_PAGE`, returning `STK_FAILED` (`0x11`) or unhandled responses.
  2. **Baud Rate Mismatch**: Optiboot standard baud is `115200`. Older ATmegaBOOT bootloaders use `57600`.
- If bootloader readback is unsupported by the installed bootloader, in-circuit serial programming (ISP) via a dedicated programmer (USBasp, Arduino as ISP) is the only alternative. ISP is a user-confirmed fallback, never automated.

### Hardware Lock Bits (Read Protection)
- The ATmega328P features hardware lock bits (`LB1`, `LB2`, `BLB01`, `BLB02`, `BLB11`, `BLB12`):
  - **Mode 1**: No memory lock features enabled. Read and write permitted.
  - **Mode 2**: Programming disabled; verification (readout) permitted.
  - **Mode 3**: Further programming and verification (readout) of Flash and EEPROM are disabled.
- **Strict Prohibition on Chip Erase**: The only hardware method to clear AVR lock bits is a **Chip Erase** (`avrdude -e`), which unconditionally wipes all Flash and EEPROM memory. MICROCODE INSPECTOR will **never** perform a chip erase or alter fuse/lock bits. If lock bits block readout, the tool reports `PROTECTED_READ_BLOCKED` and halts.

### Erased Byte Handling & Reconstruction
- Unprogrammed AVR Flash memory defaults to `0xFF`.
- AVRDUDE may omit trailing `0xFF` blocks in Intel HEX output. MICROCODE INSPECTOR reconstitutes the full 32 KiB memory map and flags unwritten trailing blocks as `UNPROGRAMMED/ERASED (0xFF)` rather than erroneously claiming truncated firmware.

### Flash vs. EEPROM Separation
- **Flash Memory (32 KiB)**: Stores program instructions and constant data in non-volatile ROM space.
- **EEPROM (1 KiB)**: Separate non-volatile memory space used for user configuration and runtime state.
- **SRAM (2 KiB)**: Volatile working memory cleared on power loss.
- Flash, EEPROM, and SRAM have independent address spaces and must never be conflated.

## 4. Operational & Browser Constraints

1. **Browser Compatibility**: The W3C Web Serial API is supported exclusively on Chromium-based desktop browsers (Google Chrome, Microsoft Edge, Opera v89+). Mozilla Firefox, Apple Safari, iOS, and Android browsers do not support Web Serial.
2. **Context Security**: Web Serial requires a secure context (`https://` or `http://localhost` / `http://127.0.0.1`).
3. **Execution Interruption**: Reading Flash requires resetting the microcontroller into its serial bootloader. **This temporarily halts the running user application.** The installed application will be preserved, and the board will be reset to normal boot after read completion, but real-time sensor logging or actuator control will be paused during extraction.
4. **Host Serial Drivers**: The host operating system must have functional USB-UART bridge drivers installed (CP2102, FTDI FT232, CH340, or Arduino 16U2 CDC ACM).
