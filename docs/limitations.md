# Technical Limitations and Boundary Disclosures

MICROCODE INSPECTOR provides transparent embedded firmware extraction and analysis. To ensure technical integrity and prevent false expectations, this document details the boundaries, physical constraints, and irreversible transformations inherent to embedded binary analysis.

---

## 1. Fundamental Binary Analysis Realities

### The Compilation Gap
A compiled firmware binary is **not** the original source code (`.ino`, `.c`, or `.cpp`). During compilation and linking:
1. **Source Comments and Documentation**: Completely stripped by the compiler preprocessor.
2. **Preprocessor Macros**: Evaluated, expanded, or omitted; `#define`, `#ifdef`, and compiler flags leave no metadata in Flash.
3. **Variable and Function Names**: Stripped by the linker. Local stack variables are reduced to register allocations or stack pointer offsets (e.g., `sp + 8`). Global variables are reduced to raw memory addresses.
4. **Data Structures and Types**: C/C++ `struct`, `class`, and `enum` definitions are flattened into memory offset offsets and byte alignments.
5. **Control Flow Transformations**: The compiler optimizer (e.g., GCC `-O2`, `-Os`) unrolls loops, inlines functions, reorders instructions, vectorizes operations, and eliminates dead code.

### Disassembly vs. Pseudocode Reconstruction
- **Disassembly** (`Assembly`): Recovers the exact sequence of CPU instructions executed by the processor. This is mathematically verifiable and represents the **ground truth** of the binary.
- **Pseudocode** (`Reconstructed Logic`): A synthetic approximation generated by analyzing control flow graphs, register usage, and standard idioms. It is an **interpretive hypothesis**, never the original source code. All pseudocode generated by MICROCODE INSPECTOR is explicitly tagged with confidence ratings and labeled as synthetic.

## 2. ESP32 Target Limitations

### Flash Encryption
- **Mechanism**: ESP32 provides hardware Flash encryption (AES-XTS-256 on classic ESP32, AES-128-XTS on others) using an internal key stored in write-protected eFuses (`BLOCK1` / `BLOCK_KEY0`).
- **UART Readback Behavior**: When Flash Encryption is enabled in development or release mode, reading Flash via the UART ROM bootloader returns encrypted ciphertext or fails if ROM read is disabled.
- **Policy**: MICROCODE INSPECTOR does **not** attempt to bypass, crack, or subvert Flash Encryption. If ciphertext or encrypted headers are detected, the tool tags the image as `ENCRYPTED/CIPHERTEXT` and halts analysis of code sections.

### Secure Boot and Download Mode Disabling
- **Secure Boot**: Validates RSA or ECDSA digital signatures of the bootloader and app partitions. Secure Boot alone does not encrypt Flash, but is frequently paired with Secure Download Mode.
- **Secure Download Mode**: When enabled (`DIS_DOWNLOAD_MODE` or `UART_DOWNLOAD_DIS` eFuse), the ROM bootloader permanently restricts or disables serial download operations. If a chip refuses serial connection due to blown eFuses, readout is physically blocked.

### Partition Layout Variations
- ESP-IDF applications use configurable partition tables (custom CSV). While the default offset is `0x8000` (and `0x9000` in certain configurations), non-standard custom bootloaders may relocate the partition table. MICROCODE INSPECTOR probes standard locations and reports if a valid partition table signature is absent.

## 3. Arduino Uno / ATmega328P Target Limitations

### Bootloader Command Support
- The Arduino Uno R3 uses the **Optiboot** bootloader communicating via the STK500v1 protocol over USB-UART (ATmega16U2 or CH340).
- While Optiboot specifications define `STK_READ_PAGE` (`0x74`) for Flash reading, certain bootloader builds or third-party clones omit readback support to save bootloader flash space (minimizing bootloader footprint to 512 bytes).
- If the connected bootloader responds with `STK_FAILED` or invalid synchronization (`0x15` / `SYNC_ERROR`), readback over UART is impossible without an external hardware ISP programmer.

### Hardware Lock Bits
- The ATmega328P contains lock bits (`LB1`, `LB2`, `BLB01`, `BLB02`, `BLB11`, `BLB12`):
  - **Mode 1**: No memory lock features enabled.
  - **Mode 2**: Further programming of Flash and EEPROM disabled in Parallel or Serial programming mode.
  - **Mode 3**: Further programming and verification (readout) of Flash and EEPROM disabled.
- **Strict Boundary**: Clearing AVR lock bits requires a full **Chip Erase** (`avrdude -e`), which unconditionally erases all Flash and EEPROM memory. MICROCODE INSPECTOR will **never** perform a chip erase or alter lock bits. If lock bits block readout, the tool reports `PROTECTED_READ_BLOCKED` and stops.

### Trailing Erased Padding Handling
- Unprogrammed AVR Flash memory contains `0xFF` bytes.
- AVRDUDE may omit trailing `0xFF` bytes in Intel HEX output. MICROCODE INSPECTOR explicitly reconstructs the standard 32 KiB memory map and flags unprogrammed sectors as `UNPROGRAMMED/ERASED (0xFF)`, preventing false reporting of truncated firmware.

## 4. Operational & Browser Constraints

1. **Browser Compatibility**: The Web Serial API is supported exclusively on Chromium-based desktop browsers (Google Chrome, Microsoft Edge, Opera, Brave). Mozilla Firefox, Apple Safari, and all mobile browsers do not support Web Serial.
2. **Context Security**: Web Serial requires a secure context (`https://` or `http://localhost`).
3. **Execution Interruption**: Reading flash memory requires resetting the target microcontroller into its serial bootloader. **This temporarily halts the running user application.** The application will be preserved, and the board will be reset to normal boot after read completion, but real-time sensor logging or motor control will be paused during extraction.
4. **Host Serial Drivers**: The host operating system must have functional USB-UART drivers installed (CP2102, FTDI FT232, CH340, or Arduino 16U2 CDC ACM).
